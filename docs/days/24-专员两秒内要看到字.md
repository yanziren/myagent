**3. [亲手] 下午：连续批处理模拟器（40 分钟）**

新建 `claimdesk/serving/batch_sim.py`。这是第 78 题的教学模拟，服务核赔台的等待预算，不接 GPU、不加载模型权重。

`simulate(arrivals, batch_cap) -> dict`。`arrivals` 是请求列表，每项有 `prefill_ms` 和 `tokens`。调度规则写死这三条：

- 每个解码步，已完成的请求离开批次，队列里的新请求补入，直到 `batch_cap`
- 某步的耗时等于 `1 + batch_size * 0.2` 毫秒，记为这一步的 `tpot_ms`（每 token 时间）
- 返回 `mean_tpot` 和每个请求的 `ttft_ms`（从到达到产生第一个 token）

测试：同样 8 个请求，`batch_cap=1` 的 `mean_tpot` 小于 `batch_cap=8` 的 `mean_tpot`。再用一个长 `prefill_ms=500` 的请求插在短请求中间，断言短请求的 `ttft_ms` 在「整批一起等长 prefill」的对照函数里更大。对照函数 `static_batch` 让整批一起进一起出。你只需要证明连续补入不会让短请求陪跑到长请求结束。

```bash
pytest tests/test_day24_latency.py -v
```

**解决什么问题**

林晓说协查转圈两分钟没字，她已经改去翻纸质条款。只缩短模型生成，不看轮数这个乘数，专员仍然要等最后一轮才看见字。用平均延迟代表体验，会把偶尔特别慢的那几次藏起来。

拒绝的方案：上线一台 GPU 推理集群来学习第 78 题。

留下的机制：2 秒内第一条进度，简单协查 20 秒内收束。独立只读工具并行。进度事件先于最终建议。模拟器演示批大小和每 token 时间的张力。

**技术原理**

一次响应的时间大约是各轮的模型时间加工具时间，再乘轮数。减少轮数是乘数。并行只读工具把相加变成取最大。进度事件不减少真实工作，但把等待变成可见过程，林晓才不会离开页面。

首 token 时间随上下文变长。第 12 天的截断直接缩短 prefill。稳定前缀才有机会命中缓存，今天在笔记里写一句：系统提示不要每轮塞入当前时间戳。

推理批处理的矛盾是吞吐和延迟。连续批处理让做完的请求离开，避免短请求陪跑。批太大时每 token 时间变差，交互式的核赔台要把这个时间压在专员能接受的范围内。模拟器里的 `0.2` 是教学系数，用来把矛盾变成断言，不是硬件参数。

**坑**

**坑 1：进度事件和最终建议同一时间戳。** 测试要求进度更早。先 `mark("progress")`，工具和模型完成后再 `mark("final")`。

**坑 2：并行函数把短信也放进去。** 发送不是只读。并行名单从 `stateless_gate` 的 `allow` 来。

**坑 3：模拟器里 batch 越大 tpot 越小。** 那是把吞吐误写成延迟。公式是批越大，每步越慢。断言方向是 `batch_cap=8` 的 `mean_tpot` 更大。

**卡住时先看这里**

- 睡眠测试在 CI 上会抖。允许 50 毫秒，不要断言等于 800。
- `static_batch` 与 `simulate` 用同一批 arrivals，才能比较短请求的 ttft。
