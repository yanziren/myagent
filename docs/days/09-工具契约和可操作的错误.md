**1. [亲手] 写三个只读工具的契约（40 分钟）**

`claimdesk/tools/schemas.py` 与 `claimdesk/tools/errors.py`。

`ToolError` 字段：`code`、`message`、`retryable`、`suggestion`、`kind`。`kind` 用 `param` 或 `execution`。

`tool_spec("get_claim_history")` 返回的字典包含：

- `side_effect == "read"`
- `retryable is True`（这是工具在瞬时故障下可否机械重试；参数错误另说）
- `schema` 是 JSON Schema 字符串，里面有 `policy_no`，示例含 `POL-1842`

`HistoryArgs`：`policy_no` 与 `user_id` 都可选，描述里写明 `user_id` 不能填保单号。只有 `user_id`、没有 `policy_no` 时返回：

- `code="PARAM_USER_ID"`
- `retryable=False`
- `suggestion` 含「改用 policy_no」
- `kind="param"`

查到保单后，返回同一被保险人的其他案件。POL-1842 必须带出 `CLM-2026-1831`。

`get_policy` 查无此保单时，`kind="execution"`，`retryable=False`，不要标成参数错误。

Schema 通过之后，执行前读 `actor_id`。林晓只能看见自己租户里的案件。用她的身份查询别人的 `claim_id` 必须拒绝，拒绝条件写在服务端查询里，不写进 Prompt。

**解决什么问题**

历史案件工具的参数叫 `user_id`，模型把保单号填了进去，接口 400。林晓只看到系统错误，连点了三次。参数错误也原样重试，只会把同一次 400 再打两遍。

拒绝的方案：用同一次请求的最大重试次数掩盖 400。也不把越权检查写进 Prompt。

留下的机制：Pydantic 写明保单号和只读副作用。错误带回原因、不可重试和建议。模型改用 `policy_no` 后才查到 CLM-2026-1831。参数错误和执行错误分开记。

**技术原理**

工具层的要求是原子、自描述、副作用写清楚。它不含「先查历史再检索」这种业务流程，谁都可以调用。Schema 是模型唯一可靠的说明书：字段名、示例、哪些枚举合法。

错误分两类。参数、404、权限不足是确定性的，原样重试没有新信息。超时、429、5xx 才值得机械重试，那是第 10 天。模型层的「智能重试」是把结构化错误交回去，让它改参数或换工具。两层不要合成一个「最多 5 次」。

`kind` 分开记，是第 30 题参数正确率的数据来源。全局成功率会把这个 400 摊平，第 21 天再做切片。

**坑**

**坑 1：建议写成「请重试」。** 模型会再送同一个 `user_id`。建议必须指向 `policy_no`。

**坑 2：`user_id` 错误被标成 `execution`。** 测试要求 events 里出现 `param`。校验失败在进业务查询之前返回。

**坑 3：Schema 里没有示例。** `POL-1842` 必须出现在 `tool_spec` 的 schema 字符串里。示例比形容词更能约束参数。

**卡住时先看这里**

- Pydantic 的 `model_json_schema()` 再 `json.dumps(..., ensure_ascii=False)`，中文描述才不会变成 `\u` 转义。测试只要求子串 `policy_no` 和 `POL-1842`。
- `ToolFailure` 是异常，`ToolError` 是返回值。参数错误走返回值，避免和超时共用一个 except 后被重试。

**验收标准**

- [ ] 错误的 `user_id` 不会进入退避，`retries == 0`
