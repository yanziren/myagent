**解决什么问题**

周衡丢来一份 20 万的争议案。单 Agent 把医学材料、条款和判例三份原文都读进上下文，token 记 9000，四分钟后同时写出无异常和异常。若所有协查都拆成三个工人，0901 每天也要付三份上下文。若按「调用一次模型」这种动作来拆，交接成本会盖过工作量。门槛本身是函数返回值，今天不写队列。

拒绝的方案：所有协查都拆成三个工人。按单次模型调用拆任务。今天也不为每个工人插入队列行。

留下的机制：只有争议案启动编排者和三个工人，只读查询并行。工人返回摘要，token 记 23。医学说异常、条款倾向通过，结论不能是通过。非争议案不会启动三个工人。

**技术原理**

多 Agent 是瓶颈倒逼出来的。三类瓶颈：上下文放不下、子任务要并行、需要独立的提示词和权限。20 万争议案踩中了前两类。0901 一条规则就能判，不在其中。

拆分粒度看交付物，不看动作。医学意见、条款引用、判例要点各自可以验收。单次工具调用太细，整份原文太粗。通信 token 相对总 token 若高到没有信息量，就是拆细了。今天 23 对 9000，通信远小于被省下的原文。

编排者收集摘要后做一致性仲裁。发现冲突就不要合成「通过」。写作步骤若在缺一方意见时补一句「无异常」，是第 18 天要堵的洞。今天先保证冲突证据都留下，决策不是通过。

**坑**

**坑 1：eligibility 也返回 `workers == 3`。** 分流写在 `handle_case` 的第一行：不是 `dispute` 就工人数为 0。

**坑 2：摘要里仍塞入 `FULL_DOCS`。** `tokens` 会变成 9000，测试要求它小于单 Agent 的 tokens。

**坑 3：冲突时取「通过」，因为条款工人是这么写的。** 决策看 finding 集合。集合里同时有异常和通过，结果是复核。

**卡住时先看这里**

- `run_parallel` 用线程。函数要无共享写。测试里的计数器加锁，你的工人不要改同一份结论字符串。
- 日课正文必须含「9000」「23」「非争议」三个子串，`tests/test_day17_multi.py` 会读本篇。

**验收标准**
