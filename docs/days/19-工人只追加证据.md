**解决什么问题**

条款工人和反欺诈工人都去改同一段结论。后写上去的「建议通过」把市三医院短期多次就诊盖掉了。给长任务加一把大锁，两名工人会互相等待到超时。让工人直接写最终结论，后写的人就赢了。今天用图把证据隔开，状态不进检查点表。

拒绝的方案：把第 8 天的简单循环改写成图。今天也不把图状态写入检查点表。

留下的机制：每个工人只把自己的证据追加进独立列表。LangGraph 用状态、合并函数、检查点和合并前中断。冲突升到周衡的复核队列，两份证据都保留。简单循环仍然是手写的。

**技术原理**

LangGraph 适合多 Agent 的几点，今天都碰到了。边是显式的，不靠提示词约定谁先写结论。状态是共享黑板，`operator.add` 规定并发追加而不是覆盖。检查点让 `get_state_history` 能看见合并前的快照。`interrupt_before` 把人工复核插在合并节点前：人还没看，决策函数就不会把两份倾向收成一句话。扇出到两名工人、再扇入合并，是这条争议路径需要的形状。

简单协查没有共享写，也没有人工中断。把它搬进图，抽象成本大于收益。测试锁住源码，防止以后「统一框架」时把第 8 天的循环也换掉。

共享资源的首选是隔离后再合并，而不是长锁。锁的持有时间在 Agent 任务里会很长。两份证据无法自动取舍时，升级到周衡，两份都留在 `evidences` 里。

**坑**

**坑 1：`evidences` 没用 reducer，后一个节点返回的列表替换了前一个。** 最终笔记会缺「条款」或缺「市三医院」。注解用 `operator.add`。

**坑 2：中断写在 `interrupt_after` 合并节点。** `paused.next` 要等于 `("merge",)`，也就是还没执行合并。人看到的是两份证据，不是已经写好的「通过」。

**坑 3：在 `loop.py` 顶部写了注释「将来可换 langgraph」。** 子串检查会失败。注释也算源码。

**卡住时先看这里**

- 第一次 `invoke` 在中断处返回。继续执行用 `invoke(None, config)`，不是再次传入 `initial`。再次传入空 `evidences` 会按 reducer 再追加一轮，或把状态搞乱。
- `thread_id` 使用 `"1842"`，和检查点键一致。
