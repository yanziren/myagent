**今日产出**

一套分段归因。先天性疾病被答成「一律不赔」时，你能指出这是切分把条款切碎了，答案不在召回里。另一条对照例证明：答案明明在召回里，却被无关片段带偏，那是生成问题。周衡能看见当时读了哪几段。归因写在测试断言里，今天不为此单开接口，也不落库。


标了 **[亲手]** 的自己写。标了 **[AI]** 的，你先把约束写清楚再生成：归因标签、条款原文不要让它改。生成之后用 pytest 验收。

**1. [亲手] 对照条款原文（10 分钟）**

AK-2024-6.1 的原文是：投保前已患的先天性疾病不赔。投保后新发的先天性疾病按住院医疗责任赔付。先天性疾病不是一律不赔。

若系统回答「先天性疾病一律不赔」，先不要换模型。

**2. [亲手] 记录每次召回，并做出切碎的对照（50 分钟）**

文件：`claimdesk/rag/attribute.py`，配合 `claimdesk/rag/chunk.py` 里的一种固定长度切分。

对问句「先天性疾病是不是一律不赔」：

1. 用固定长度窗口把 AK-2024-6.1 切碎，使「投保前已患的先天性疾病不赔」和「不是一律不赔」落在不同窗口，top-k 拿不到那句完整条件。
2. 函数返回归因标签，测试期望这条被标成检索阶段的切分问题，而不是生成模型问题。
3. 日志里保留召回片段原文。周衡要能读到「当时读了哪几段」。

再准备一条对照：召回片段里已经有完整句子，草稿却答成一律不赔。这条标成生成问题。可以是忽略了正确句子，或被同时召回的无关窗口带偏。

归因清单写进函数的返回或笔记，两段都要有：

- 检索：库里有没有、切分有没有把句子切开、召回有没有、排序是否把正确片段截在 top-k 之外
- 生成：忽略、误解、多段整合错误，还是编造了召回里没有的内容

检索段和生成段的结论只存在测试断言中。不要为了像服务而给归因单独开端口。空检索仍作答的门禁在第 13 天。

**3. [亲手] 跑归因测试**

```bash
pytest tests/test_day06_attribute.py -v
```

期望：先天性疾病这条例的归因是切分，不是模型。

**4. [AI] 可以帮你列举生成侧的四种失败，不能改归因结论**

提示词附上 AK-2024-6.1 全文，要求它列出「一律不赔」可能来自哪一段被单独召回。你自己决定标签。没看日志之前，不要接受「换一个更大的模型」这种建议。

**解决什么问题**

系统把先天性疾病答成一律不赔。条款写的是投保前已患的先天性疾病不赔。周衡看不到当时读了哪几段。没看检索日志就换模型。日志和归因都留在测试里，不单开服务。

拒绝的方案：把生成提示词或模型当成第一嫌疑。也不为归因单独部署服务。

留下的机制：先看召回片段里有没有那句话。固定长度切碎之后，这条例归到检索阶段的切分原因。

**技术原理**

一个「答错了」要切成两段：检索给了什么，模型拿着这些生成了什么。答案不在召回里，继续往下看知识库、解析、切分、查询措辞、排序。答案在召回里，再看忽略、误解、多段整合和编造。

生产 RAG 的错误里，切分和解析占了很大一部分。团队的第一反应常常是改生成提示词。纪律是：没看检索日志之前，不下「是模型不行」的结论。

今天的固定长度切分是用来制造失败的仪器。第 7 天会改成按条、款、表整块切分，把这条例修好。两天合在一起，才是第 56 题的完整排查。

**坑**

**坑 1：切碎之后又用手把正确句子拼回 prompt。** 现象：归因函数看到的召回是完整的，标签只能落在生成侧，测试失败。修法：归因用的就是切碎后的 top-k，不要旁路。

**坑 2：日志只存条款号，不存片段正文。** 周衡无法判断「读到了没有」。日志至少包含片段文本和条款号。

**坑 3：对照例忘了做。** 只有切分失败的话，你还不会区分生成问题。笔记里要有一条「召回里有原句，草稿仍然一律不赔」。

**卡住时先看这里**

- 条款全文在 `CLAUSE_V3`，用字符串查找确认原句存在，这证明是切分问题而不是知识库缺失。
- 窗口长度选会把「投保前已患」和「不是一律不赔」拆开的那个值，并把它写进测试可见的参数，不要依赖偶然的换行。
