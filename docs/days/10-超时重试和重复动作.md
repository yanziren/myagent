**今日产出**

超时才指数退避，一次调用最多两次等待（1 秒、2 秒）。同一工具名加规范化参数第三次不再执行，上下文里注入「必须换策略或声明无法完成」。步数上限和 token 预算是另外两道保险丝。参数错误仍然不重试。写操作先插入 `idempotency` 行，键是 `job_id + 工具名 + 规范化参数`，不用时间戳。同一键再次执行返回第一次结果。


标了 **[亲手]** 的自己写。标了 **[AI]** 的，你先把约束写清楚再生成：可重试错误码、退避序列、指纹规则不要让它改。生成之后用 pytest 验收。

**1. [亲手] 只对瞬时错误退避（40 分钟）**

`claimdesk/agent/loop.py` 里可机械重试的 code：`TIMEOUT`、`429`、`500`、`502`、`503`。它们由 `ToolFailure` 抛出。

一次 `_call` 最多三次尝试。前两次失败把当前间隔记入 `delays`，间隔从 1 开始，每次翻倍。第三次失败把错误返回给循环，`retries` 增加 `len(delays)`。所以一次超时调用贡献退避 `[1, 2]`，`retries` 加 2。

`PARAM_*` 这种 `ToolError` 不进入这段循环。第 9 天的 `retries == 0` 必须仍然成立。

```bash
pytest tests/test_day09_tools.py tests/test_day10_loop.py -v
```

写操作在第一次调用前插入 `idempotency`，`status=intended`。键是 `job_id + 工具名 + 规范化参数`，禁止用时间戳或随机 UUID。成功后改为 `done` 并记下结果。同一键再执行时返回第一次结果，`retries` 不增加。参数错误不进入这张表。

**2. [亲手] 指纹第三次停手（30 分钟）**

指纹是 `工具名 + ":" + json.dumps(args, sort_keys=True, ensure_ascii=False)`。

- 第 1、2 次相同指纹：正常执行（超时的话各自退避 `[1, 2]`）
- 第 3 次：不调用工具，把观察文本设为「必须换策略或声明无法完成」，指纹写入 `bill["blocked_fingerprints"]`

测试把 `get_claim_history` 换成永远 `ToolFailure("TIMEOUT")` 的函数，模型在看到那句提示之前一直用 `{"policy_no": "POL-1842"}` 再调。期望：

- `bill["retries"] == 4`
- `bill["backoff"] == [1, 2, 1, 2]`
- `blocked_fingerprints` 非空
- 某一轮 prompt 含「必须换策略或声明无法完成」
- 模型随后给出的决策是「无法完成」

这 4 次重试是两轮调用各退避两次，不是「同一个计数器数到 4」。

**3. [亲手] 步数和 token 分开停**

`Budget(max_steps=3, max_tokens=20000)`：模型每次都换一个新的 `policy_no`（指纹不重复），`stop_reason == "step_cap"`，`len(trace) <= 3`。

`Budget(max_steps=8, max_tokens=1)`：第一轮 prompt 的 token 估算已经超过预算，`stop_reason == "token_budget"`，`trace == []`。token 估算用 `max(1, len(text) // 4)`。

两道保险丝不要合成一个「最多 5 次」。

**解决什么问题**

历史案件接口一直超时。模型用同一参数连续调用，晚上的假账单被重试放大。一个「最多重试 5 次」同时对付超时、参数错误和死循环，会把不该重试的也重试，并且要烧完次数才停。

拒绝的方案：对所有错误使用同一个重试上限。写操作的自动重试留到有幂等键之后，短信在第 11 天，恢复在第 23 天。今天用查询演示。幂等键不能用重试当时新生成的 UUID。

留下的机制：超时才指数退避，一次调用最多两次等待。同一指纹第三次不执行，改为注入「必须换策略或声明无法完成」。步数和 token 预算是另外两道保险丝。

**技术原理**

死循环来自「工具没有带来新信息」。超时返回的是同一句错误，模型就再选同一个动作。大循环和「参数改一个空格」是变体。指纹抓的是完全相同的调用。第 3 次不杀进程，而是把一句可操作的话写进上下文，模型常常能自己停。

步数上限防的是步数爆炸。token 预算防的是每步都不同、但上下文在膨胀的漫游。测试用 `max_tokens=1` 让第二道在第一步之前就停，证明它不依赖步数计数器。

重试的新问题是重复副作用和成本放大。查询可以退避；没有幂等键的短信不能照抄今天的逻辑。账单字段 `retries` 和 `backoff` 要分开可见，后面做「重试后才成功」的监控才有数。

**坑**

**坑 1：第三次仍然调用了工具。** 指纹计数要在 `_call` 之前。先加计数，`>= 3` 就 `continue`。

**坑 2：退避间隔写成三次 `[1, 2, 4]`。** 测试要的是一次调用 `[1, 2]`，两轮共 `[1, 2, 1, 2]`。第三次尝试不再等待，直接把错误交回去。

**坑 3：参数错误也被 `ToolFailure` 包了一层。** 那样第 9 天的 `retries` 不再是 0。参数错误保持返回 `ToolError`。

**卡住时先看这里**

- 指纹必须 `sort_keys=True`，否则键顺序不同会被当成两次新调用。
- `max_tokens=1` 时，循环在调用模型之后、执行工具之前就要返回。trace 仍为空，因为工具还没进 `trace`。看 `finish("token_budget")` 的位置：它在 `model()` 之前返回，所以模型也不会被叫到产生工具。对照 `loop.py`：先渲染 prompt，token 不够就 `return finish("token_budget")`。

**验收标准**

- [ ] `pytest tests/test_day10_loop.py tests/test_day09_tools.py -v` 通过
- [ ] 超时两轮的 backoff 是 `[1, 2, 1, 2]`，然后出现换策略提示
- [ ] 步数帽和 token 预算的 `stop_reason` 不同
- [ ] 参数错误的重试次数仍是 0
