**2. [亲手] 实现 `evaluate_eligibility`（50 分钟）**

文件：`claimdesk/rules/eligibility.py`

```python
def evaluate_eligibility(claim, policy, waiting_days: int, model=None) -> Suggestion:
    ...
```

`model` 参数只为了证明这里不会调用它。函数体内不要调用 `model`。判定顺序：

1. `policy.status != "active"` 或产品不是案件上的产品 → 拒绝，条款 `AK-2024-4.2`，规则号 `R-POLICY-INACTIVE`
2. `(claim.admission - policy.issue_date).days < waiting_days` → 拒绝，条款 `AK-2024-3.1`，规则号 `R-WAITING-PERIOD`。理由里写明实际间隔天数和等待期天数
3. `claim.hospital` 不在 `policy.hospitals` → 拒绝，条款 `AK-2024-8.1`，规则号 `R-HOSPITAL`
4. `claim.amount > policy.limit_amount` → 拒绝，条款 `AK-2024-7.1`，规则号 `R-LIMIT`
5. 其余 → 通过，条款 `AK-2024-4.2`，规则号 `R-ELIGIBLE`，`model_calls` 保持默认 0

这是 Workflow 层里的一个确定性节点。LLM 不掌握控制流。

规则函数之后增加路由。`claimdesk/api/app.py` 提供 `POST /claims/{claim_id}/eligibility`，请求体含 `actor_id`。用 `TestClient` 和临时 SQLite 打 0901：`claims` 多一行，响应 `model_calls` 为 0，测试不占端口。资格计算不要进入模型网关。

**解决什么问题**

林晓问 CLM-2026-0901 保单是否有效、等待期过了没有。这种问题每天上百次，专员等不了一次模型。路径在设计时就能穷举，循环只会增加费用和不确定性。

拒绝的方案：用会自己决定下一步的循环回答资格问题。也不只在 Prompt 里禁止调用模型。

留下的机制：有效期、等待期、医院和限额走规则编号。0901 零次模型调用，建议通过。1842 投保后 13 天，规则直接拒绝并引用等待期。

**技术原理**

Tools、Workflow、Agent 三层里，今天写的是 Workflow 的一个节点，而且这个节点连模型都不用。工具是原子能力，Workflow 是开发者写死的控制流，Agent 把「下一步」留到运行时。资格问题属于中间层里最便宜的那一种：纯规则。

理赔审批里大量判断是确定性的。规则能判定的不进模型，这是成本和可靠性同一刀。新需求以后可以先用 Agent 探索；这条路径已经稳定，它就该留在规则里，而不是第 8 天再被拖进循环。

**坑**

**坑 1：日期用了出院日。** 现象：1842 出院是 2026-04-07，间隔变成 18 日，若等待期被改成 15 日会误过。等待期看入院日减投保日。13 日这个数要能在理由字符串里看见。

**坑 2：桩函数被「安全地」调用了一次。** 现象：你在函数开头写了 `if model: model("")` 想打日志。测试直接失败。修法：`del model` 或完全不引用它。

**坑 3：通过时引用了等待期条款。** 0901 通过的条款是保障范围 `AK-2024-4.2`。等待期条款只出现在等待期拒绝上。

**卡住时先看这里**

- `Suggestion` 的字段在 `claimdesk/domain/models.py`。`rule_ids` 默认空列表，通过 `rule_ids=` 传入。
- 等待期天数来自调用方参数 `waiting_days`，函数内部不要写死 30。第 15 天 V4 会传入 90。
