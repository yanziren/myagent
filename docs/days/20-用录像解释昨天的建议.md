**1. [亲手] 记录一步的完整现场（40 分钟）**

`claimdesk/traces/store.py` 的 `TraceStore`：

- `start()` 返回 `tr-1` 这种编号
- `record(trace_id, **event)` 追加事件。事件含 `tool`、`args`、`result`、`reason`、`context_before`、`context_after`
- `checkpoint(trace_id, state)` 把状态放进该 trace 的 `checkpoints`

用 1842 记两步，对应昨天 15:10 的协查：

1. `get_claim_history`，参数 `{"policy_no": "POL-1842"}`，结果 `{"claims": ["CLM-2026-1831"]}`，理由「先查历史就诊」。`context_before` 是「完整历史很长」，`context_after` 是「摘要：已查历史」。两者必须不相等
2. `search_clauses`，参数 `{"query": "等待期"}`，结果条款 `AK-2024-3.1`，理由「再用历史结果查条款」

然后 `checkpoint(..., {"step": 2, "claim_id": "CLM-2026-1842"})`。

每步先插入 `audit`，`phase=intent`，带 `trace_id`、`tool`、`payload`，然后再执行。执行完再写 `phase=result`。测试可以在只有 intent 时停下，断言外部调用尚未发生。回放按 `trace_id` 读 SQLite，不读进程内存。

**2. [亲手] 重放不打实时接口（20 分钟）**

`replay(trace_id, live)` 忽略 `live`。测试传入的 `live` 一被调用就把计数加一。期望计数仍是 0，重放顺序是 `get_claim_history` 然后 `search_clauses`。

`first_divergence(trace_id, ["get_claim_history", "get_policy"])` 返回 `index == 1`，`actual == "search_clauses"`。吴严问的「从哪一步开始和预期不一样」，答案是第二步工具名。

**3. [亲手] 结果分和轨迹分分开（20 分钟）**

`score_outcome("通过", "通过")` 为真。结果对，只说明终点标签一致。

`trajectory_violations` 对下面四步要同时包含三个标记：

- `send_sms` 且 `approved` 为假 → `unauthorized`

结果可以通过，轨迹仍然不合格。不要把三种违规折进一个「成功」布尔值。

**解决什么问题**

吴严要解释昨天 15:10 为什么曾建议拒绝 1842。今天重跑，工具返回和措辞都变了。只保存最后一条聊天，出了问题只能请模型回忆当时读了什么。

拒绝的方案：把不可复现的现场当成评估。重放时再调一次历史接口。

留下的机制：同一条 trace 编号记下摘要前后的上下文、工具参数、返回和本步理由，并写检查点。重放走录像。结果分可以是通过，轨迹分仍会抓住未审批发送、死循环和没有证据的结论。

**技术原理**

结果评估看终点：标签对不对、条款号在不在。轨迹评估看路径：工具是否该调、有没有未审批的写、是否原地打转、结论有没有证据。结果对而过程病态，是生产系统的定时炸弹。只看轨迹也会冤枉另一条合法路径，所以两条都要，结果分做主指标，轨迹分做红线。

调试多 Agent 时，错误分布在编排、工人和合并三处。trace 编号把它们串起来。摘要前后的上下文都要留下，否则你无法判断是摘要把证据压没了，还是模型没读到。检查点是第 23 天恢复的地基，今天先把「能按编号取回状态」做出来。

重放必须确定性。实时工具的返回会变，昨天的 15:10 就解释不清。`live` 被删掉不用，是这条纪律的测试形态。

**坑**

**坑 1：重放时调用了 `live`。** `calls["n"]` 变成 1。`replay` 只读 `events` 里的 `result`。

**坑 2：只存 `context_after`。** 测试比较前后不相等。摘要前的长文也要留，第 12 天的压缩才查得到。

**坑 3：轨迹违规用「有任意一步不对就返回 False」。** 测试要同时看到 `unauthorized`、`loop`、`no_evidence` 三个字符串。一个列表才能指导修复。

**卡住时先看这里**

- `first_divergence` 按工具名序列比较。预期第二步是 `get_policy`，实际是 `search_clauses`，index 从 0 数，所以是 1。
- 指纹循环：列表里同一个 `fingerprint` 值出现至少 3 次就记 `loop`。测试给了三步 `send`，其中第一步还带未审批。

**验收标准**

- [ ] `pytest tests/test_day20_trace.py -v` 通过
- [ ] 重放不调用 `live`，顺序与录像一致
- [ ] 偏离点的 index 是 1，actual 是 `search_clauses`
- [ ] 结果分为通过时，轨迹违规仍含未审批、循环、无证据
